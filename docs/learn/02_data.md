# 2. The data

The project uses six datasets. Each answers a different question, so it helps to know each one's **job**, not just its name. All raw files live under `data/raw/` (set by `DATA_DIR` in [src/config.py](../../src/config.py)); that folder is not on GitHub because the data licences don't allow redistribution.

| Dataset | Job in the project | Path |
|:---|:---|:---|
| Synthetic | A lab with a known, planted signal: does the method find it? | generated by code |
| Coinbase BTC-USD | The main real test: predictable, and profitable after fees? | `data/raw/crypto/BTC_1sec.csv` |
| Coinbase ETH-USD | Does Ethereum's book help predict Bitcoin? | `data/raw/crypto/ETH_1sec.csv` |
| LOBSTER (Nasdaq) | Sub-second horizons; large-tick vs small-tick stocks | `data/raw/lobster/` |
| FI-2010 | Compare with the published DeepLOB paper | `data/raw/fi2010/...` |
| Optiver Realized Volatility | How much did the Kaggle winner rely on future information? | `data/raw/optiver_rvp/` |
| Optiver Trading at the Close | A second, different prediction problem with drifting data | `data/raw/optiver_close/train.csv` |

## The common format: 40 numbers per snapshot

Every order-book dataset is converted into the same layout so the same features and models work on all of them. One snapshot = one row of 40 numbers:

```
[ask_price_1, ask_size_1, bid_price_1, bid_size_1,   <- level 1
 ask_price_2, ask_size_2, bid_price_2, bid_size_2,   <- level 2
 ...
 ask_price_10, ask_size_10, bid_price_10, bid_size_10]  <- level 10
```

So column 0 is the best ask price, column 1 its size, column 2 the best bid price, column 3 its size, and every 4 columns is one more level. In the code this array is always called `lob_40`.

## Synthetic data

**What it is.** A simulated order book generated by [src/data/synthetic_generator.py](../../src/data/synthetic_generator.py). Nothing is read from disk.

**How it's made.**
- A book with 10 levels, a $100 starting price and a 1-cent tick. In the "large-tick" regime the spread is almost always one tick.
- Events arrive about every 10 ms: 40% market orders, 40% new limit orders, 20% cancellations.
- **The planted signal:** now and then an "informed trader" switches on for 15–60 events. While on, market orders go 85/15 in one direction, new limit orders lean 70/30 toward that side, and cancellations hit the other side. So the book visibly tilts before the price moves.
- Each session is 60,000 events (about 10 minutes). We use 5 sessions (seeds 0–4).

**Why it matters.** Because we *know* the signal exists and how long it lasts (15–60 events), we can check that the pipeline finds it and that skill peaks at the right horizon. It cannot tell us anything about real markets.

## Coinbase BTC-USD

**What it is.** A Kaggle dataset ("High Frequency Crypto Limit Order Book Data", CC0 licence) recorded from Coinbase: one snapshot per second from 7 to 19 April 2021, about 1.03 million rows.

**One raw row** (simplified, first row of the file):

| column | value | meaning |
|:---|:---|:---|
| `system_time` | 2021-04-07 11:32:42 | when the snapshot was taken |
| `midpoint` | 56035.995 | mid price in USD |
| `spread` | 0.01 | one tick |
| `buys`, `sells` | 0, 0 | USD of market buys / sells since the last snapshot |
| `asks_distance_0` | ~0 | level-1 ask price as a *fraction away from the mid* |
| `asks_notional_0` | 1902.29 | USD resting at the level-1 ask |
| `bids_notional_0` | 3061.86 | USD resting at the level-1 bid |
| ... | | the same for levels 0–14, plus `*_limit_notional`, `*_market_notional`, `*_cancel_notional` per level |

**How it becomes `lob_40`** ([src/data/crypto_loader.py](../../src/data/crypto_loader.py)):
1. Price at each level = mid × (1 + distance), rounded to the 1-cent tick.
2. Size in BTC = USD notional / price.
3. Only levels 0–9 are used (10 levels).
4. A trade tape for VPIN is rebuilt from `buys` and `sells`: one buy record and one sell record per second.
5. The result is cached as `BTC_1sec.L10.npz` so later runs load in seconds.

**How it's used.** The ~1.03 M rows are cut into **4 contiguous segments of 257,682 rows (about 3 days each)**. Each segment is treated as an independent repeat of the whole experiment with its own train/validation/test split, so every result is a mean ± std over 4 segments.

**Order flows.** The `*_limit_notional`, `*_market_notional` and `*_cancel_notional` columns say how much was added, traded and cancelled at each level since the last snapshot. They feed the "order flow" features in Experiments H, I and J (cached as `BTC_1sec.flows.L5.npz`). One caveat: per-level market flow only adds up to 30–40% of total traded volume, so it's incomplete.

**ETH-USD** (`ETH_1sec.csv`) has the same format and dates. Experiment F aligns it to BTC by time.

## LOBSTER (Nasdaq)

**What it is.** Free academic sample files from lobsterdata.com: **every order event** for five stocks on 21 June 2012, 9:30–16:00, with 10 book levels. Two files per stock:

**Message file** (one row per event):

| time (s after midnight) | type | order id | size | price | direction |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 34200.0057 | 4 | 15835012 | 34 | 275200 | −1 |
| 34200.0062 | 1 | 16114545 | 100 | 275200 | −1 |

Event types: 1 = new limit order, 2 = partial cancel, 3 = full cancel, 4 = visible execution, 5 = hidden execution. Prices are in dollars × 10,000, so 275200 = $27.52. Direction −1 = a sell order.

**Orderbook file** (the book after each event, same row order): `275200, 66, 275100, 400, ...` = best ask $27.52 for 66 shares, best bid $27.51 for 400 shares, and so on.

**How it's used** ([src/data/lobster_loader.py](../../src/data/lobster_loader.py)):
- The event stream is resampled onto a **100 ms clock**: each row is the book as it stood at that moment, so horizons like "500 ms" or "5 s" become a fixed number of rows (5 or 50).
- Executions between rows become the trade tape; adds, trades and cancels per level become order-flow features.

**The two groups:**

| | Tick as share of price | Spread at one tick | Typical size at best price |
|:---|:---:|:---:|:---:|
| INTC, MSFT (large tick) | 3.3–3.7 bp | 77% of the time | ~13,000 shares |
| AAPL, AMZN, GOOG (small tick) | 0.17–0.45 bp | under 1% | ~100 shares |

Only one day per stock, so treat LOBSTER results as a case study.

## FI-2010

**What it is.** The standard academic benchmark (Ntakaris et al., 2018): 5 Finnish stocks on Nasdaq Nordic over 10 trading days in June 2010. It comes **already processed**: one row per 10 order-book events, already normalised (z-scored), with 144 features and the labels attached.

**The file layout is unusual:** each file is a table where *rows are features and columns are time steps*. Rows 1–40 are the raw book (10 levels), rows 41–144 are hand-made features (spreads, mid-prices, price differences, derivatives, intensities), and the last 5 rows are labels for horizons k = 10, 20, 30, 50 and 100 events. [src/data/fi2010_loader.py](../../src/data/fi2010_loader.py) transposes it.

**Setup 2** (what the DeepLOB paper used and what we use): train on days 1–7 (`Train_..._CF_7.txt`), test on days 8, 9 and 10 (`Test_..._CF_7/8/9.txt`).

**Its labels:** UP if the *average* of the next k mid prices is more than 0.2% above the current mid, DOWN if more than 0.2% below, otherwise FLAT. Averaging makes the labels smooth and easier to predict than raw moves; keep that in mind when you see high accuracies.

## Optiver Realized Volatility (Kaggle 2021)

**What it is.** About 112 stocks, each with thousands of 10-minute windows (`time_id`). The task is to predict how volatile each stock will be in the **next** 10 minutes. This is a regression problem, not direction prediction.

- `book_train.parquet`: per second, the best two bid/ask prices and sizes. Prices are normalised to 1.0 at the start of each window (e.g. `bid_price1 = 1.0014`).
- `trade_train.parquet`: trades per second: price, size, number of orders.
- `train.csv`: the target for each (stock, time_id), e.g. `0.0041` = 0.41% realised volatility.

**The catch:** Optiver shuffled the `time_id`s so you couldn't tell their order. The winning team recovered the real order anyway and used "neighbouring" windows, including windows from the **future**. Our experiment measures how much of their gain that future information was worth.

## Optiver Trading at the Close (Kaggle 2023)

**What it is.** The Nasdaq **closing auction** for 200 stocks over 481 days, 5.2 million rows. Each row is one stock at one of 55 moments in the last 10 minutes of the day.

Key columns: `imbalance_size` (shares that can't be matched yet), `imbalance_buy_sell_flag` (which side has the excess), `reference_price`, `matched_size`, `bid_price`, `ask_price`, `wap`, and the **target**: how much the stock's price moves over the next 60 seconds relative to an index, in bp.

**How it's used:** train on days 0–399 and hold out days 400–480, exactly as the winning team did, and compare a model trained once with one retrained every 12 days.

## Check yourself

1. Why does every order-book dataset get converted into the same 40-column layout?
2. Why is the BTC data split into 4 segments instead of used as one long series?
3. In a LOBSTER orderbook row, what does `275100, 400` in columns 3 and 4 mean?
4. Why should you be cautious when comparing FI-2010 accuracies with BTC accuracies?

<details><summary>Answers</summary>

1. So that one feature pipeline and one set of models work on all of them, and results are comparable.
2. Each segment is an independent repeat of the experiment, which gives a mean and a standard deviation, a measure of how stable the results are.
3. The best bid is $27.51 (275100 / 10,000) with 400 shares waiting.
4. FI-2010 labels are based on the *average* of future prices (smoother, easier), it uses 10-event rows instead of 1-second rows, and it's 2010 Finnish stocks. The numbers aren't on the same scale.
